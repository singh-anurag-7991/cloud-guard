Shield

Rate limiting that holds when someone hammers your API.

Open source

The problem

Every public API eventually meets a client with a retry loop and no backoff, a credential-stuffing script, or one customer who accidentally sends 40× their normal traffic on a Tuesday morning.

Without a limiter, a single caller degrades the service for everyone else. The database saturates, latency climbs, and the incident looks like a capacity problem when it was really one bad client.

What Shield does

Shield sits in front of your API and decides, per API key and per endpoint, whether a request gets served or gets a 429. State lives in memory for a single instance, or in Redis when you run more than one.

Correct by default

Returns proper 429 responses with X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset headers — so a well-behaved client can back off on schedule instead of guessing and retrying straight into the same wall.

Four algorithms, and when to reach for each

Token bucket

Refills at a fixed rate and allows short bursts up to the bucket size.

Use when: traffic is naturally bursty — which is nearly always. This is the default.

Leaky bucket

Drains at a constant rate regardless of how requests arrive.

Use when: the thing behind the API cannot absorb bursts at all — a downstream with fixed throughput.

Fixed window

Counts per clock window. Cheapest to compute, but allows up to double the limit across a window boundary.

Use when: the limit is generous and the boundary edge case does not matter.

Sliding log

Keeps a timestamp per request per key. Most accurate, most memory.

Use when: the boundary loophole is exploitable and precision is worth the RAM.
